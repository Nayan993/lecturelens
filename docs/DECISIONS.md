# LectureLens — Decision Log

Append-only. **Newest first** — add new rows at the top of the table. Never edit or delete
an existing row; to reverse a decision, add a new row that supersedes it and names the old one.
Contract-affecting decisions must also be reflected in [`CONTRACTS.md`](./CONTRACTS.md).

| Date | Decision | Made by | Why |
| --- | --- | --- | --- |
| 2026-11-02 | The `/ask` relevance gate has a second, script-independent signal: a question also reaches the LLM when one retrieved passage contains **all** of its content words (lexical coverage), not only when its best cosine ≥ `RAG_MIN_SCORE`. Supersedes the 2026-11-01 "cosine only" gate row. | Member D | The English-only embedding model squashes cosine on Hindi–English lectures: "what is association" scored 0.215 against a passage explaining association, so answerable questions abstained. On evaluation/rag no unanswerable question reaches full coverage (max 0.75), so the gate is as strict for them as before; generation-side checks still apply. |
| 2026-11-02 | `503 PROVIDER_UNAVAILABLE` from `/ask` and question generation adds `details.retryAfterSec` and a `Retry-After` header when the provider said how long to wait; the LLM client fails fast instead of retrying when that wait exceeds its 20 s limit. Additive: `details.provider` is unchanged. | Member D | A daily token quota (Groq: 200 000 tokens/day for openai/gpt-oss-120b) asks for ~9-minute waits; retrying three times only delayed an inevitable 503 by ~1 minute and made users re-ask. The message now says when to try again. |
| 2026-11-01 | Member C's implementation follows CONTRACTS.md where the playbook (PC.1–PC.3) differs: hybrid stays **reciprocal-rank fusion** (§5.6), not min-max + alpha fusion; retrieved passages have no `topicLabel` (§6.7); question generation returns `201 { items }` synchronously (§5.7), not 202; `PATCH /questions/:id` takes `{ status, rejectionReason, … }`, not `{ action }`; `POST /quizzes` uses all approved questions when fewer than requested and is `422` only when none exist; attempts are open to any signed-in user who can open the quiz (§1.6); another user's attempt or quiz is `404`, not `403` (§1.5). | Member D | The frozen contract is the source of truth; the client and mocks are built on it. A change to any of these would be a separate contract change. |
| 2026-11-01 | The `/ask` retrieval-side relevance gate compares `RAG_MIN_SCORE` (default 0.35) with the **cosine similarity** between the question and the best retrieved passage, for all three retrievers; `topScore` stays on the retriever's own scale (§5.6). | Member D | RRF scores depend only on ranks (the top hit always scores ≥ 1/61, max 2/61) and BM25 is unbounded, so neither can say "nothing relevant"; the old 0.35 compared with RRF made every hybrid question abstain. 0.35 was calibrated on evaluation/rag (19/20 answerable questions reach the LLM, 6/10 unanswerable are stopped before it). |
| 2026-11-01 | Keyword retrieval is hand-written **BM25** over the chunk text in scope (k1 1.5, b 0.75), not Mongo `$text`/`textScore`; CONTRACTS.md §5.6 updated. | Member D | Implemented by Member C per the playbook; tokenises Unicode letters (Hindi–English transcripts), and scores are testable without a database. Only the documented score scale changed. |
| 2026-10-28 | Upload accepts optional `recordedOn` (`YYYY-MM-DD`) and `notes`; lectures serialise `recordedOn` (notes are stored, not serialised in v1). Accepted media adds `.mkv` (`video/x-matroska`) and the common wav/m4a MIME aliases; the server decides type by extension + sniffing. | Member D | The upload form collects the recording date and notes; cards can show when a lecture was given rather than when it was uploaded. Browsers report MIME types inconsistently (often empty for .mkv). |
| 2026-10-28 | Add `GET /quizzes` (owner C): the caller's quizzes as `QuizSummary` (topics covered, question count, attempt count, best score, last attempt). | Member D | The quiz list must show coverage and "your best score"; the contract had no way to list quizzes or past attempts. |
| 2026-10-28 | Grounded answers carry `topScore`: the best retrieval score among the passages considered (null if none). | Member D | Shown as grounding evidence in the Ask UI, and it explains a `NO_RELEVANT_PASSAGE` abstention (top score under the threshold) — important for the viva. |
| 2026-10-28 | Lecture objects gain two computed, read-only fields: `uploadedByName` and `topicCount` (visible sections for the caller; null before segmenting). Not stored; added at serialisation (CONTRACTS.md §5.3, §6.1). | Member D | LectureCard shows the teacher and topic count; without these the library would need a user lookup plus one topics request per card. |
| 2026-10-28 | Two seeded demo accounts (teacher@lecturelens.dev, student@lecturelens.dev, password "lecturelens") are part of the contract (CONTRACTS.md §9); the mock adapter and the server seed use exactly these, and the seed never runs in production. | Member D | The login page offers one-click demo sign-in for the viva; a single documented source stops the client mock and the server seed drifting apart. |
| 2026-10-27 | Every route listed in `CONTRACTS.md` is mounted from day one; until its owner implements it, it returns `501 NOT_IMPLEMENTED` with `details: { owner, prompt }`. Fabricated success data from server routes is forbidden. | Member D | Four people build in parallel; a stable route map lets the client integrate early, and a loud 501 can't be mistaken for a working feature the way fake `200` data can. |
| 2026-10-27 | All media offsets are float seconds rounded to 3 decimals, named `startSec` / `endSec`; `hh:mm:ss` strings and integer milliseconds are forbidden for media positions. | Member D | The HTML5 player seeks with `video.currentTime = 612.34`, ASR returns seconds, and one unit end-to-end removes a whole class of conversion bugs between transcript, chunks, topics, citations and deep links. |
| 2026-10-27 | Two-process architecture: one React/Vite client and one Express API server. The media pipeline (FFmpeg, transcription, chunking, embeddings, LLM calls) runs in-process inside the API with status persisted on the lecture document — no Python service, worker process, job queue, Redis or separate vector database. | Member D | Smallest system a four-person team can run, debug and deploy; MongoDB Atlas already holds the data and its indexes, and lecture volume does not justify extra infrastructure. |
